`id` includes starters for the main brand-layer path and a smaller direct-app path.

## Brand layer

Use this when the brand should become an importable Nuxt layer.

```bash [Terminal]
npx giget@latest gh:happydesigns/id/templates/brand-layer my-brand
cd my-brand
pnpm install
pnpm verify
pnpm dev
```

The starter contains:

- `brand.ts`
- `app/app.vue` with the standard Nuxt UI `UApp` root
- `app/app.config.ts`
- `app/assets/css/brand.css`
- a starter logo component rendered on the homepage
- public favicon
- Nuxt layer export

`brand.ts` owns the reusable neutral definition, including structured runtime assets with accessible labels and light/dark media hints. `app/app.config.ts` exposes those assets and maps the same definition to Nuxt UI, while the starter logo component renders them through `IdLogo`. Optional guide prose remains a separate export and is not shipped to every consuming app.

## Direct themed app

Use this for prototypes or small apps that own their pages and want to use `@happydesigns/id` directly before extracting a separate brand layer.

```bash [Terminal]
npx giget@latest gh:happydesigns/id/templates/themed-app my-app
cd my-app
pnpm install
pnpm verify
pnpm dev
```

The starter contains:

- a Nuxt app extending `@happydesigns/id/nuxt`
- the standard Nuxt UI `UApp` root in `app/app.vue`
- one local primary theme
- a page using `useBrandTheme`
- standard Nuxt UI components

## Starter rule

Starters are project scaffolds, not brand doctrine. Keep durable identity rules in `brand.ts` and product behavior in the app that owns it. For public reusable apps, prefer a neutral app plus an external brand layer.

The repository test suite includes starter smoke checks so these projects keep resolving `@happydesigns/id/nuxt`, app-config wiring, and global component usage after package changes.
