title: Brand Studio
description: Create a reusable Nuxt UI brand, preview real applications and review changes before applying them.
---

[Open Studio](/studio?browse=true). The brand picker searches configured brands and saved drafts. Its **Manage brand** submenu creates, imports and duplicates projects; **Export** reviews and downloads changes. The product link on the left returns to the host application. The category buttons open the shared **Brand editor**. On smaller screens, **Editor** opens it and its category selector provides the same settings. Closing the editor reveals the unchanged preview.

Use **Brand picker → Manage brand → Manage brands** to search browser-saved projects, open, rename or duplicate them, and delete a local copy after confirmation. Names must be distinct. Deleting the current copy returns to the Nuxt UI baseline. Configured brands and repository files are not deleted; Nuxt UI remains available in the brand picker.

Standard preview fills the available space without handles or size fields. The device button switches to Responsive, with mobile, tablet, laptop and desktop presets; switching back preserves the last dimensions. Fixed viewports accept custom width and height (240–3840 CSS pixels) and can rotate. Studio scales large previews to fit without changing their layout width; both comparison frames use the same dimensions. View links preserve the dimensions. These controls test responsive layouts, not touch input, pixel density or browser/device emulation.

In Responsive mode, drag the right, bottom or corner grip on the outer frame to resize the viewport without covering its content. Focus a grip and use arrow keys for single-pixel changes, or Shift for ten-pixel changes. The **View** popover contains preview controls at every screen size. Light, Dark and System remain directly accessible in the toolbar.

Reloading reopens the last active saved brand or configured baseline automatically. General status and error messages use Nuxt UI toasts with stable IDs; field validation stays next to its input. During drag resizing, comparison previews share a stable zoom, and Escape cancels the current gesture.

On this documentation site, the selected Studio profile also styles the docs. Edits follow you back through the product link and survive a reload in the same browser. These local previews do not modify the repository or change other visitors' themes.

## Generate a brand reference

Add `@happydesigns/id/guide` to the authoring host and use `IdBrandReference`.
It reads the same `appConfig.idStudio.document` as Studio, or an explicit
`document` prop. Its `section` prop accepts `all`, `colors`, `typography`,
`icons`, `styles` or `assets`. In Docus, use:

```md
::id-brand-reference{section="colors"}
::
```

Palettes, mappings, font stacks, radius, component overrides and asset downloads
come from the source. Dark values inherit light declarations unless overridden.
Unspecified settings are marked as Nuxt UI defaults. The color section measures
selected opaque text/surface pairs in the current browser appearance using the
[WCAG contrast formula](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html);
it does not certify an entire brand or application. Images and downloads use
local asset paths; arbitrary remote or executable URLs are not rendered.

Studio's Docs preview updates both the theme and the reference data, including
the separate original and draft frames. New-project exports with the optional Docus guide include the guide
layer and a source-driven Brand reference page. Production consumers of the
exported brand still receive only native app config, CSS and assets.

Keep palette intent, logo rules and voice in authored guidance. The reference
does not invent those decisions from token values.

## Add Studio to a host

Studio is an optional authoring layer for a Nuxt UI application. Consumers of an exported brand receive native CSS, app config and assets; they do not need the id runtime or Docus.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: ['@example/brand', '@happydesigns/id/studio']
})
```

```ts [app/app.config.ts]
import document from '../brand.studio.json'

export default defineAppConfig({
  idStudio: {
    document,
    sourcePath: 'brand.studio.json',
    home: '/',
    documentation: '/guide',
    host: {
      name: 'Example/brand',
      logo: { light: '/logo.svg', dark: '/logo-inverse.svg' }
    }
  }
})
```

Use the import path to your actual source file.

New native exports have a public `@example/brand/styles.css` fragment. Extending
the layer supplies app config and components, but does not register CSS. In a
plain Nuxt UI app, register `~/assets/css/main.css` and import `tailwindcss`,
`@nuxt/ui`, then `@example/brand/styles.css` there. Nuxt UI discovers layer sources.
Docus already supplies the framework entry: import only the brand fragment in
`app/app.css`, as generated playgrounds do. No CSS merge hook is needed.

The existing `{ legacyRuntime: true }` export and old runtime layers retain their
previous behavior for compatibility; migrate them deliberately, not by removing
framework imports without replacing runtime-applied theme variables.
The `createStudioRuntimeFiles(document)` helper also preserves the old CSS-entry
default for previously exported generators. New projects explicitly pass
`{ styles: 'fragment' }`. When migrating an older native project, update its
generator, public stylesheet export, layer config and host import together.

The product link at the top left returns to `home` in the same tab. `host`
provides the application's stable name and optional light/dark logo, independently
of the brand being edited. Without it, Studio shows `happydesigns/id`. The Docs
link opens `documentation` in another tab; it falls back to `home` for existing
hosts. Leaving Studio warns only when changes could not be saved locally.

Set `host.logo.kind` to `wordmark` when the asset already contains the brand name.
Studio displays the complete asset on its own, preserving its proportions without
appending product text. `host.name` still identifies the home link for assistive
technology and its tooltip. The default `symbol` form keeps the full name beside
a square mark. Product names use neutral text rather than the edited draft's
accent color.

Template cards render the actual template at a 1280 × 800 viewport with the current
draft and resolved color mode. They load only while the picker is open and the
card is visible, with at most two frames starting concurrently. Closing the picker
unmounts the miniatures. Their navigation and messages cannot switch the main
preview. Route preview layers must isolate fixture state, as they do for comparison
frames; thumbnail routes carry `frame=thumbnail`. Optional `thumbnail` image paths
serve as a fallback if a live preview fails.

## Manage several brands

The picker includes the host brand, saved browser projects and a protected **Nuxt UI** baseline. Choose **Create brand** from that baseline to start an independent project. Brand selection updates only the previews; it does not switch the host application's runtime theme. Light, Dark and System remain separate display controls.

Creating or duplicating a brand requires a distinct name. Cancelling the name dialog or browsing unchanged catalog brands does not create a saved project. Existing documents with the same display name remain intact; the picker distinguishes them by package and saved time. Editing a brand's name in the inspector can give older drafts a more useful name.

Use **Open brand** to import a source document, or register reviewed documents in the host's app config:

```ts [app/app.config.ts]
import document from '../brand.studio.json'
import clientBrand from '../brands/client.studio.json'

export default defineAppConfig({
  idStudio: { document, brands: { client: clientBrand } }
})
```

Keep catalog keys stable so each brand retains its own draft and comparison baseline. These documents are public application configuration, not repository credentials. Local asset paths must be served by the host; use distinct paths for different brands. Imported documents do not connect repositories or grant file access.

Configured additional brands and imported brands support local drafts and downloads. Only the host's explicitly configured source has an Apply connection. Returning to that brand rechecks the source revision before allowing a saved draft to be applied. The picker never guesses a repository path from a package name.

## Preview real applications

Components and Landing are included. A capability can register its existing scenario as an async component, sharing code and fixtures with its own playground. Studio supplies `document`, `mode` and `page`; `navigate(pageId)` synchronizes the comparison frames.

Docs uses your host application's real Docus routes, Markdown, navigation and search. Add Docus to the authoring host and register a bounded route subtree:

```ts [app/app.config.ts]
export default defineAppConfig({
  idStudio: {
    templates: {
      docs: {
        label: 'Docs',
        description: 'Navigation, search, prose and code examples.',
        owner: 'docus',
        route: '/docs/introduction',
        routePrefix: '/docs'
      }
    }
  }
})
```

This configuration is trusted application code. An imported brand cannot register routes or execute components. Frames stay on the same origin and within the configured subtree. One host server renders Studio and its previews. Selecting a template does not add that capability to the exported brand.

The header separates brand selection from preview type. The brand picker has its own pill; the adjacent group switches directly to Components or opens the visual Templates gallery.
Components uses the 21 examples from Nuxt UI's Theme Studio, including authentication,
account tabs, contributors, shortcuts and chat controls. Cards keep the original
composition and order in responsive masonry lanes; all examples remain accessible
on smaller screens. Actions are local demonstrations, not connected services.
Templates can provide a `thumbnail` using a local public asset URL
such as `/previews/docs.webp`. Keep the image with the capability that owns the
preview. Without an image, the picker shows a layout icon. Thumbnails are static
orientation images; only the selected preview renders the active brand live.

## Customize a draft

The header offers **Ask AI** and **Export**; both are also available in the Studio menu.
Ask AI currently prepares a question with the active brand's colors, typography and
theme configuration for copying into an external assistant. It does not send a
request or modify the brand. The dialog explicitly indicates that integrated AI
chat is not connected.

The editor overlays the preview without resizing it. **Pin editor** explicitly reserves space beside the preview on wide screens; **Unpin editor** returns to overlay mode. The URL remembers the open category (`editor`) and pin preference (`docked`) on reload. With no editor selected, Studio opens in preview mode. The categories Brand, Colors, Typography, Appearance and Components share one editor; palette creation, import and export remain separate tasks. Package metadata and custom CSS font stacks live under Advanced. Palette selectors show color swatches; New palette opens a separate dialog with an empty name, a base color and generated shades. Creation does not assign a role. Existing palettes show their role usage and offer Rename and Delete through their actions menu; deleting an assigned palette requires a replacement. The palette picker suggests neutral Nuxt scales for Neutral and chromatic scales for other roles. Custom brand scales appear in their own group without automatic classification; assigning one to a role is explicit. Show all palettes exposes other choices, and existing assignments remain visible. Single colors belong in appearance or asset values, while role mappings require palettes. Primary and neutral colors are immediate controls; additional roles and existing component overrides are disclosed when needed. Logo uploads support PNG, JPEG and WebP up to 2 MB; existing local SVG references are preserved. Font stacks use fonts already available in the application and do not install fonts.

Compare shows the loaded or applied baseline beside the draft. Both use the same page and color mode, with independent interaction state. System, Light and Dark apply to the shell and preview together. View links contain only navigation, mode and comparison settings, never brand documents.

Unknown metadata, additional asset roles and component configuration survive editing. CSS classes still need to exist in the host's compiled styles; the preview cannot compile arbitrary classes from imported JSON. Contrast feedback measures body text against the page background, not every component or interaction state.

## Review and apply locally

A host can explicitly connect one absolute JSON path in private runtime configuration:

```ts [nuxt.config.ts]
import { fileURLToPath } from 'node:url'

export default defineNuxtConfig({
  extends: ['@happydesigns/id/studio'],
  runtimeConfig: {
    idStudioSource: fileURLToPath(new URL('./brand.studio.json', import.meta.url))
  }
})
```

Only the local development server registers this writer. **Changes** opens a field-level review. **Apply changes** validates and atomically replaces the connected JSON source after checking its revision. If another editor changed the file, Studio preserves the draft and refuses to overwrite it. Download the draft before reopening the connected project to resolve the conflict. New, imported and duplicated projects stay disconnected until explicitly reopened from the host.

The host owns regeneration of derived files. Exported projects include a generator and a source watch hook; an existing host should call its own generator when the source changes. Writing the JSON does not commit, publish or deploy anything.

## Download and recover

Download opens a choice between a portable brand file and a generated Nuxt project. Changes, Source and CSS remain available in a stable-height review dialog. **Download JSON** provides the complete JSON. **Download ZIP** creates a native Nuxt UI layer with generated app config, CSS, BrandLogo and available public assets. Its development playground includes Studio. Docus is added only when **Include Docus guide** is selected. Custom Vue components, capability packages and font files must be added separately.

Install the exported project, then run `pnpm dev` or `pnpm build`. Run `pnpm generate:brand` after source changes outside the running playground. Generated files are derived output; edit the JSON source.

Until id is published, a host can set `idStudio.packageAsset` to a same-origin `.tgz` path. Studio includes that reviewed package as a development dependency and as a playground asset for subsequent exports. Without this option, substitute a reviewed local package for the registry dependency.

Drafts, comparison baselines and downloaded snapshots are stored under separate project IDs in this browser. The brand picker and recovery preserve work across switches and reloads. Browser storage is not a backup. If it fails, Studio asks before replacing unsaved work. Downloading does not advance the applied baseline; a successful local Apply does.

## Scope

Nuxt UI is the supported authoring target. Historical adapter helpers and runtime exports remain compatible APIs. `createStudioRuntimeFiles` generates native runtime files; `createStudioProject(document, { legacyRuntime: true })` retains the previous id-runtime project format for existing integrations.

### Icon sets

The Icons editor previews nine icon sets. A selection updates Nuxt UI icons in Studio and the preview, and is exported as native `ui.icons` configuration. Randomize offers Icons separately and includes them in Entire look. Reset appearance restores the original icons; each change supports Undo. Supplemental gallery icons use available set-specific mappings with Lucide fallback. Non-bundled collections load through Nuxt Icon; bundle the selected Iconify collection in your project when offline availability is required.

### Editing and project menus

Use the four dock categories: Colors (roles, palettes, surfaces and contrast), Typography, Icons, and Styles (radius and component defaults). Open Brand settings from the brand picker for name, statement, logos and package metadata. Its Manage brand menu contains create, import, duplicate, manage and reset actions. The Export dialog groups Brand JSON and CSS under Code; Changes shows the comparison with the original.

## Reproducible local development packages

A registry publication is not required. Keep a reviewed ID tarball under the host repository's `vendor/` directory (identified by revision and SHA-256), and install that exact file as a development dependency. Commit the lockfile and archive, or restore the identical archive from your existing artifact storage before installation. Do not rely on a sibling ID checkout.

```sh
pnpm add -D ./vendor/id-REVISION.tgz
pnpm exec id-studio-package --source vendor/id-REVISION.tgz --public-dir docs/public --sha256 EXPECTED_SHA256
```

The command checks package identity and checksum, then copies it to a content-addressed public filename and prints its `packageAsset` URL. Configure that returned URL in `idStudio.packageAsset`. Keep it in sync when intentionally upgrading the archive. The helper never fetches, publishes, installs or discovers packages. If project export does not need a bundled authoring package, omit packageAsset entirely.

## Native Docus entry points

Keep Docus's header and footer. Place `<IdStudioLink label="Open Studio" />` in `app/components/AppHeaderCTA.vue` and the footer's native `AppFooterLeft.vue` slot so it remains reachable on mobile. Existing footer content stays in that slot. The link disappears when the optional Studio layer is removed. Set `idStudio.home` for the Studio product link and `documentation` for Docs. `host` is the stable portal identity, independent of the edited brand.

Use `satisfies StudioHostConfig` from `@happydesigns/id/studio/core` to check the host configuration. The authoring helpers and types may remain development dependencies. Published native runtime files must not import them.

## Optional Docus guide

New project exports start with Studio, Components and Landing. Capability templates are registered explicitly by the host. Select **Include Docus guide** in Export to add documentation routes and the source-derived brand reference. The programmatic equivalent is `createStudioProject(document, { guide: true })`. Docus is not installed by the default export, and neither authoring mode adds Docus or ID to the native brand runtime. Existing Docus portals remain supported.
