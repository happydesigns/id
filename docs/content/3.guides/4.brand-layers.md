title: Brand Layers
description: Build full Nuxt brand layers with @happydesigns/id contracts and Nuxt UI defaults.
---

A brand layer is the right shape when branding owns more than runtime-safe values.

## Minimal layer

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: ['@happydesigns/id/nuxt'],
  css: ['~/assets/css/brand.css'],
  app: {
    head: {
      link: [
        { rel: 'icon', type: 'image/svg+xml', href: '/favicon.svg' }
      ]
    }
  }
})
```

The layer export registers identity helpers with the global `Id` prefix. If a host app needs a different prefix, use the module integration instead:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@happydesigns/id/module'],
  id: {
    componentPrefix: 'BrandId'
  }
})
```

## App config

```ts [app.config.ts]
import { brand, brandTheme } from '../brand'
import { createNuxtUiAppConfig } from '@happydesigns/id'

const nuxtUiConfig = createNuxtUiAppConfig(brandTheme)

export default defineAppConfig({
  id: {
    name: brandTheme.name,
    theme: brandTheme,
    assets: brand.assets
  },
  ui: nuxtUiConfig.ui
})
```

Nuxt does not require `id.theme`. `id` uses it as the typed source for validation, generated CSS variables, playground previews, runtime-safe theme switching, and Nuxt UI app-config derivation.

Keep package-owned brand data in `brand.ts` or an equivalent source file. Keep `app.config.ts` thin: import the theme and structured assets, generate Nuxt UI app config, and expose the public runtime-only `id` contract. Only a dedicated guide app should add `id.guide`.

## Layer ownership

Brand layers can provide:

- public assets
- metadata
- CSS token definitions
- Nuxt UI defaults
- logo components
- app shell wrappers
- docs styling

They should not provide product permissions, storage behavior, API contracts, or workflow rules.

## Migrate an existing brand guide

When an existing brand guide moves onto `id`, migrate the reusable Nuxt UI mechanics before deleting brand-specific implementation.

1. Move the typed neutral definition, target mappings, and optional guide shape into package-owned source files such as `brand.ts`.
2. Validate the neutral colors, typography, and structured assets with `defineBrand()`, then map palette families to Nuxt UI roles and component defaults through `nuxtUiAdapter`.
3. Keep brand-specific copy, logo doctrine, palette meaning, asset files, voice, and documentation in the brand layer.
4. Wire `app.config.ts` through `createNuxtUiAppConfig(brandTheme)` so the layer exposes one primary `id.theme` and `id.assets`, without automatically shipping guide content.
5. Extend `@happydesigns/id/nuxt` from the brand package, then remove duplicated runtime helpers only after the brand still builds and documents the same decisions.

For `@happydesigns/brand`, this means `id` should absorb reusable guide mechanics and Nuxt UI mapping helpers. The brand package should keep final happydesigns doctrine, assets, page copy, logo rules, and voice.

## Multi-brand deployments

For deploy-time brand selection, keep the app brand-neutral and select the layer in `nuxt.config.ts`.

```ts [nuxt.config.ts]
const brandLayer = process.env.NUXT_BRAND_LAYER ?? '@client/default-brand'

export default defineNuxtConfig({
  extends: [brandLayer]
})
```

This keeps one app source while allowing deployment-specific brand expression.

For development against an unpublished brand layer, clone or download the layer into `layers/90.brand` and run the app normally.

```bash [Terminal]
npx giget github:client/brand layers/90.brand
pnpm dev
```

`90.brand` is a convention, not a Nuxt requirement. It makes the layer order obvious in projects that rely on Nuxt's auto-scanned `layers/` directory. If an app already has late override layers, choose a name that keeps the brand after base layers and before intentional local overrides.
