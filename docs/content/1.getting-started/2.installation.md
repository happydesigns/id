For new native brands, use Studio's New project export or the native brand-layer starter. Install ID as a development dependency (a reviewed versioned tarball is supported before publication). Consumers extend the exported brand and explicitly import its `styles.css`; they do not install ID or Docus.

The steps below describe the existing identity-runtime integration for applications that deliberately use ID runtime helpers.

::code-group
```bash [pnpm]
pnpm add @happydesigns/id tailwindcss
```

```bash [npm]
npm install @happydesigns/id tailwindcss
```

```bash [yarn]
yarn add @happydesigns/id tailwindcss
```

```bash [bun]
bun add @happydesigns/id tailwindcss
```
::

## Extend the base layer

Existing identity-runtime brand repositories extend the reusable `id` Nuxt layer, then add their own assets, CSS, app shell pieces, and `app.config.ts`.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: ['@happydesigns/id/nuxt']
})
```

## Use the module

Use the module when the project wants explicit module options instead of extending the base layer.

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@happydesigns/id/module'],
  id: {
    name: 'client',
    componentPrefix: 'Id'
  }
})
```

`Id` is the default global component prefix. Keep it unless your app already owns component names such as `IdLogo`, `IdThemeSelect`, or `IdColorModeButton`.

The module declares Nuxt UI as a module dependency for the `Id*` components. Register `@nuxt/ui` yourself only when the host app needs to customize Nuxt UI module options directly.

## Configure the brand

Expose the primary brand identity through `app.config.ts`. This mirrors Nuxt UI's own configuration model: public, serializable defaults live in app config; files, assets, layouts, and server behavior stay in the Nuxt layer or product app.

For reusable brand repositories, keep the actual brand source in a normal file such as `brand.ts`, then import it from `app.config.ts`. That keeps the brand testable and exportable while still using Nuxt's standard app-config model.

```ts [brand.ts]
import { defineBrand } from '@happydesigns/id'
import { nuxtUiAdapter } from '@happydesigns/id/adapters/nuxt-ui'

export const clientBrand = defineBrand({
  name: 'client',
  packageName: '@client/brand',
  claim: 'The reusable identity guide for Client.',
  colors: {
    blue: { 500: '#2563EB' },
    slate: { 500: '#64748B' }
  },
  assets: {
    logos: {
      logo: {
        name: 'Client logo',
        src: '/favicon.svg',
        role: 'logo',
        alt: 'Client'
      }
    }
  }
})

export const clientTheme = nuxtUiAdapter.transform(clientBrand, {
  label: 'Client',
  colors: {
    primary: 'blue',
    neutral: 'slate'
  },
  cssVariables: {
    light: {
      '--ui-bg': 'white',
      '--ui-text': '#334155',
      '--ui-text-highlighted': '#020617'
    }
  }
})
```

```ts [app.config.ts]
import { createNuxtUiAppConfig } from '@happydesigns/id'
import { clientBrand, clientTheme } from '../brand'

const nuxtUiConfig = createNuxtUiAppConfig(clientTheme)

export default defineAppConfig({
  id: {
    name: clientTheme.name,
    theme: clientTheme,
    assets: clientBrand.assets
  },
  ui: nuxtUiConfig.ui
})
```

This is the runtime-only shape. A dedicated guide app may additionally expose a separately defined `id.guide`, but ordinary consuming apps do not need guide prose or coverage data.

The default Nuxt UI baseline can be imported from `@happydesigns/id/themes/nuxt-ui`. The neutral sample theme used by these docs lives at `@happydesigns/id/themes/sample-brand`. Treat that local theme as an example of the integration shape; `@happydesigns/brand` owns the final happydesigns brand source.

## Apply a brand layer

A brand-neutral app can consume a brand layer directly, without changing product code.

```ts [nuxt.config.ts]
const brandLayer = process.env.NUXT_BRAND_LAYER ?? '@client/brand'

export default defineNuxtConfig({
  extends: [brandLayer]
})
```

The consuming app should still set its own `compatibilityDate` in `nuxt.config.ts`. The `id` layer has a compatibility date for its own development and starter projects, but an app-level value is the deployment contract for the product that extends it.
