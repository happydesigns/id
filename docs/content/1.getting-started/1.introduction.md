`@happydesigns/id` is the reusable identity system for brand guides, Nuxt UI app-config defaults, and Nuxt brand layers.

Use it when a project needs a stable way to describe and apply brand identity without moving product behavior into branding.

## What you get

::u-page-grid
  :::u-page-card{title="Identity contracts" icon="i-lucide-braces" to="/guides/brand-guide-contract"}
  Typed helpers define brand metadata, palettes, semantic roles, CSS variables, typography, voice, assets, and usage limits.
  :::

  :::u-page-card{title="Nuxt UI mapping" icon="i-lucide-palette" to="/guides/nuxt-ui-mapping"}
  Brand themes map identity decisions to Nuxt UI semantic colors, CSS variables, slots, variants, and default variants.
  :::

  :::u-page-card{title="Brand layer path" icon="i-lucide-layers-3" to="/guides/brand-layers"}
  Full brands can ship as Nuxt layers with assets, layouts, CSS, app metadata, component defaults, and docs styling.
  :::
::

## First decision

Choose the branding path by the kind of change you need.

| Need | Use |
| --- | --- |
| Logos, favicons, app shell, layouts, docs styling, custom brand primitives | Nuxt brand layer |
| Colors, typography variables, surface tokens, Nuxt UI defaults | Primary `id.theme` inside a brand layer |
| Theme picker, preview mode, tenant visual preview | Optional runtime theme list |
| Product rules, permissions, APIs, tenant behavior | Product app, not `id` |

## Keep apps brand-ready

Apps are easiest to brand when they follow Nuxt UI conventions:

- Use Nuxt UI components for common controls.
- Use `color` props and semantic utilities such as `text-default`, `bg-muted`, and `border-default`.
- Keep shared component defaults in `app.config.ts`.
- Avoid raw brand colors in reusable product components.
- Keep domain behavior independent from identity configuration.
