---
title: Apply branding
description: Consume a native brand layer and adopt changes without rewriting application features.
---

A generated brand supplies native Nuxt UI configuration, CSS and public assets. The consuming application keeps its own routes, features and explicit UI overrides.

## Install and extend the brand

Install your reviewed brand package through your registry or as an exact local archive. For example:

```sh
pnpm add @example/brand
```

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: ['@example/brand'],
  css: ['~/assets/css/main.css']
})
```

The native brand already registers Nuxt UI. It does not register framework CSS for you: import the brand fragment **after** Tailwind and Nuxt UI in the application's CSS entry.

```css [app/assets/css/main.css]
@import "tailwindcss";
@import "@nuxt/ui";
@import "@example/brand/styles.css";
```

Follow the [Nuxt UI installation conventions](https://ui.nuxt.com/docs/getting-started/installation/nuxt), including `UApp` around the application:

```vue [app/app.vue]
<template>
  <UApp>
    <NuxtPage />
  </UApp>
</template>
```

Docus already owns its framework CSS and application shell. In a Docus consumer, import only `@example/brand/styles.css` in `app/app.css`. Do not extend the brand's documentation application.

## Keep application overrides local

Application `app.config.ts` settings override extended layers, following [Nuxt layer priority](https://nuxt.com/docs/4.x/getting-started/layers#layer-priority):

```ts [app/app.config.ts]
export default defineAppConfig({
  ui: {
    button: { slots: { base: 'tracking-wide' } }
  }
})
```

Keep deliberate app-specific choices here and shared brand choices in the brand source. When connecting a branded app to Studio, follow the [preview override contract](/guides/brand-studio#preview-a-separately-running-app) so the temporary preview preserves the same ownership.

## Adopt a brand change

1. Edit `brand.studio.json` in Studio or your editor.
2. Regenerate the layer with `pnpm generate:brand`. Only the generated config and CSS are replaced.
3. Check the affected app states, then deliver a reviewed brand version or archive.
4. Update that dependency and lockfile in each consumer, then rebuild and deliver the application.

ID does not remotely update deployed apps. An app remains on its adopted version until you update it.

## Deployment-specific brands

Select a layer in Nuxt config when deployments use different brands. Keep the CSS entry consistent with the selected package; changing only `extends` while importing another brand's CSS creates a mixed identity. See [Brand layers](/guides/brand-layers) for repository structure.

## Existing runtime themes

Applications that deliberately use ID's runtime helpers can switch already-shipped themes without rebuilding. This is a separate integration described in [Runtime themes](/guides/runtime-themes). Neither runtime switching nor a native brand may own authorization, APIs, storage or product rules; see [Boundaries](/concepts/boundaries).
