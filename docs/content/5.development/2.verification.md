## Test boundaries

Tests protect ID's contracts: lossless brand documents, safe source writes, generated-file ownership, host configuration precedence, preview isolation and standalone native layers. Nuxt UI owns component internals; Changelogen owns release-note and version generation. Avoid source-string assertions, fixed padding values and tests that only repeat third-party behavior.

Use ordinary Vitest for pure transformations and filesystem behavior. Use `@nuxt/test-utils/e2e` for real Nuxt module registration and SSR. Playwright checks complete app journeys, hydration, cross-frame previews, downloads and keyboard interaction. Add a Nuxt runtime component test only when the behavior needs that environment; do not mount the whole application for pure logic.

## Commands

Run `pnpm install`, `pnpm dev:prepare` and `pnpm exec playwright install chromium` once for local setup.

| Command | Responsibility |
| --- | --- |
| `pnpm verify` | Lint, unit tests and workspace type checks |
| `pnpm test:nuxt` | Real Nuxt module, SSR, auto-imports and host overrides |
| `pnpm test:browser` | Studio, Guide, embedded and development app previews |
| `pnpm test:package` | Pack, install outside the workspace, generate native apps and test their output |
| `pnpm test:docs` | Documentation navigation, persisted appearance and template previews |
| `pnpm test:devtools` | Actual development-only DevTools edit journey |
| `pnpm test:preview` | External preview bridge in a production build |
| `pnpm verify:full` | All of the above; local release preflight |

Each integration command prepares the package itself. Filter a suite with its normal runner arguments, for example `pnpm test:browser tests/browser/showcase.spec.ts`. Documentation tests start only the docs server; package tests start only their native output servers. `ID_DOCS_TEST_URL` uses an existing docs server instead of building another one. Tests within one suite share their servers. Local commands use fixed ports, so suites using the same fixture must run sequentially.

Logic changes need focused Vitest coverage. Package and framework changes need their integration checks. Documentation-only changes need the docs build/browser suite, not native consumer builds. CI runs the complete set for code changes; keep local investigation focused.

## Browser coverage

The authoring journey imports two contrasting documents, edits their palettes, checks the catalog or dashboard preview and verifies downloaded JSON preserves assets and extension data. Desktop/light and mobile/dark cover layout and mode handling without multiplying every brand, viewport and application combination.

Separate regressions cover source conflicts, preview origin/session validation, app-state preservation, initial paint and hydration, overlays and focus. Unit tests cover the numerous invalid-input cases. Browser assertions check visible behavior and computed semantic styles rather than implementation classes or exact spacing.

The docs suite samples the baseline and two distinct presets. It checks navigation without reload, persisted edits, first paint, template recovery and bundled icons without network fallback. It does not repeat every navigation path for every palette.

## Packed consumers

`test:package` uses the standard `pnpm pack` lifecycle, then installs that archive outside the workspace. It checks public imports and resolved dependency declarations. Two generated brands exercise distinct hosts: a catalog and a dashboard. Their dependency graphs must exclude ID and Docus, and production output must omit the preview bridge. Browser checks cover brand colors, typography, logos, application overrides, interaction and light/dark responsiveness.

The input documents are deterministic fixtures, independent of prior browser runs. The Studio download test separately checks the exported document contract. Package verification also builds an exported standalone Studio and the optional Docus guide. Those authoring hosts intentionally depend on ID; the no-ID runtime rule applies to native consuming apps.

Generated manifests use the package's pinned direct dependency versions. Fresh isolated installs still resolve transitive dependencies; their temporary directories and lockfiles are retained for diagnosis. This is consumer compatibility evidence, not a claim that every transitive version is fixed by the workspace lockfile.

`prepack` only builds the package. Packing does not rerun the full suite or regenerate workspace examples. The package archive checked by the native suite is the artifact uploaded by CI.

## CI and release cost

Fast verification and Nuxt integration run independently of browser installation. The browser, docs, package, DevTools and production-preview suites run in parallel jobs. Linux minimum-Node and Windows checks retain focused package/source coverage. Browser jobs install only Chromium's headless shell and its required system dependencies.

Normal main pushes, PRs and manual runs verify the code. The main-branch run for a `chore(release): v…` commit is skipped because the version-tag run performs the full verification. Always push the release tag with that commit; if only the branch was pushed, use manual dispatch or push the tag to obtain verification. Tag runs are not automatically cancelled by a newer run. Publication waits for verification, compatibility and all integration jobs.

Local `release` currently publishes npm after local verification and before pushing. CI therefore gates the GitHub release, not that npm publication. Moving npm publication into CI is a separate workflow decision.

Failure traces and browser output are retained under `.output/tests/` and uploaded by CI. Inspect step durations before adding more jobs or caching. No fixed coverage percentage or automatic retries substitute for meaningful assertions and isolated test state.

## Real application adoption

The opt-in [capability proof](/development/capability-proof) exercises explicitly selected Course and Booking checkouts. Customer repositories are not prerequisites for ID's normal tests. For EHS, Bechtle or another adopter, also run that repository's checks against the candidate package: its assets, fonts, overrides and domain behavior remain its responsibility.

Identify an unreleased archive by SHA-256 when updating consumer tooling and embedded downloads. These checks do not publish packages or update deployments.

## Validated framework baseline

Generated projects pin shared dependencies to the versions installed for the package build. Their ID dependency follows the package release version. Scaffold manifests use catalog and workspace references, resolved during bundling. Shared ranges belong in the pnpm catalog; the package build derives Nuxt module compatibility from those same declarations. The workspace lockfile is the tested dependency graph; declared compatible ranges are not evidence that every newer combination has passed visual or hydration checks. Guide/Studio integration is tested independently from a native packed-brand consumer. Customer upgrades need their own consuming-app checks.

Tiptap follows Nuxt UI's dependency contract. The previous editor-family overrides are no longer needed with the updated Nuxt UI graph. Keep core and extensions aligned when reviewing lockfile changes and verify the production editor build; do not restore a broad override list merely to silence peer warnings.

TypeScript stays on its current major because `vue-tsc` and the package-type tests use its JavaScript compiler API. TypeScript 7 does not provide that API, and Vue's tooling still requires the previous compiler; see the [TypeScript migration guidance](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/). Avoid a second compiler or aliases until the Vue toolchain supports the native compiler. H3 and DevTools also remain on stable releases compatible with Nuxt, rather than following prerelease dist-tags.

The workspace uses pnpm's current lockfile format, including its separate package-manager document. Use the pinned pnpm version for installation and lockfile changes. Vitest uses its current defaults, including clearing mock call history between tests; individual tests must establish their own expected calls.

## Integration compatibility

The Guide preserves Vue's `onServerPrefetch` registration in production clients because it delimits `useId` ranges. The production fixture verifies form and tab associations without `ClientOnly`, through both MDC and direct Vue. See [the hydration fixture](https://github.com/happydesigns/id/blob/main/tests/fixtures/guide/README.md) for the minimal reproduction and reason. The form-label and tab-panel assertions are now required success tests. Do not restore expected failures to accommodate a dependency update.

Native Tabs demonstrations with labels only still need actual content slots when a host wants meaningful tab-panel content. This is independent of hydration.

## Support checks

Release publication also requires the compatibility job for package types and local source operations on Linux and Windows. CI reads the supported Node range from `package.json`; the explicit minimum-version case in `.github/workflows/verify.yml` must be reviewed when changing that range. These jobs test the baseline, not every dependency combination.

Dependency updates arrive as reviewable Dependabot PRs; they are not merged automatically. Review overlapping groups together when Nuxt UI and Docus share a dependency graph. Remove the Guide hydration workaround only when the fixture passes without it on the supported dependency baseline, as described in [the hydration fixture](https://github.com/happydesigns/id/blob/main/tests/fixtures/guide/README.md).
