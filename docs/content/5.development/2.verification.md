## Everyday checks

Run `pnpm install` and `pnpm prepare` for setup. `pnpm dev` starts the playground and `pnpm docs` starts Docus. Use `pnpm lint:fix` for formatting and `pnpm verify` for lint, unit tests and all type checks. Scripts in `package.json` own the exact commands. Package-type tests compile the preview configuration from the actual API reference in NodeNext and Bundler resolution; documentation tests also check every published entrypoint.

Choose checks appropriate to the change. Logic changes need focused regression coverage; public package, generation, preview and framework changes also need the integration pipeline below. Documentation-only changes need a docs build and link review, not rebuilt native consumers.

## Native branding workflow

The browser authoring pass must precede the isolated native builds; the final browser pass verifies those builds. Keep this order so each stage uses the current source.

After `pnpm install`, `pnpm prepare` and `pnpm exec playwright install chromium`, run:

```sh
pnpm pack:studio
pnpm exec nuxt generate tests/fixtures/guide
pnpm docs:build
pnpm test:authoring
pnpm check:native
pnpm test:browser
```

Keep the stages in this order; do not reuse old exports after changing the fixtures. Generated documents and measurements live in `.output/workflow/`. App source is copied unchanged into each native consumer; only its brand dependency and CSS import differ from development.

## Workflow proof

The catalog fixture exercises filtering, cart state and navigation; the dashboard exercises Nuxt UI form validation and saved state. Browser authoring imports a brand document, changes its primary palette through the editor, previews both apps in light/dark mode and downloads the resulting JSON. The native consumer check uses those exact exports from the packed ID package, builds four independent apps and checks that neither ID nor Docus appears in their dependency graph. App source and app-specific configuration stay unchanged between brands. Browser checks compare surfaces, headings, inputs, logos, buttons, form-error colors and popover styling against the preview measurements at narrow and wide widths in both color modes. They repeat the application interactions and check horizontal overflow. The fixtures deliberately keep an app override equal to the original brand value while the draft changes it, proving that explicit `appUi` wins in both preview and native builds.

These are computed-style and behavior assertions, not pixel snapshots or visual certification of arbitrary applications. Native screenshots are diagnostic artifacts under `.output/tests/`. Fonts and classes must already be available; applications still own their features and adopt brand updates through normal builds. The commands above generate fresh evidence in the required order.

The check installs the packed ID archive outside the workspace and also builds the standalone exported Studio and optional Docus guide. The no-ID/no-Docus runtime assertion applies to native consuming apps; authoring and documentation hosts intentionally use those packages. Fresh consumer dependencies resolve independently of the workspace lockfile. The retained temporary directory and its lockfile support diagnosis.

## CI and artifacts

The Verify workflow runs for pull requests, main, version tags and manual dispatch. It uses the committed lockfile, runs the checks above and retains the package and SHA-256 checksum as a versioned artifact. Browser reports and failure artifacts live under `.output/tests/`; CI uploads failure diagnostics. Fixture servers under `tests/helpers/` are test infrastructure, not package runtime.

## Validated framework baseline

Generated projects pin shared dependencies to the versions installed for the package build. Their ID dependency follows the package release version. Scaffold manifests use catalog and workspace references, resolved during bundling. Shared ranges belong in the pnpm catalog; the package build derives Nuxt module compatibility from those same declarations. The workspace lockfile is the tested dependency graph; declared compatible ranges are not evidence that every newer combination has passed visual or hydration checks. Guide/Studio integration is tested independently from a native packed-brand consumer. Customer upgrades need their own consuming-app checks.

The workspace pins Tiptap's editor family together through the workspace overrides after a mixed core/extension graph failed production bundling. This is an authoring test-workspace constraint, not a new dependency of native brand consumers.

## Integration compatibility

The Guide preserves Vue's `onServerPrefetch` registration in production clients because it delimits `useId` ranges. The production fixture verifies form and tab associations without `ClientOnly`, through both MDC and direct Vue. See [the hydration fixture](https://github.com/happydesigns/id/blob/main/tests/fixtures/guide/README.md) for the minimal reproduction and reason. The form-label and tab-panel assertions are now required success tests. Do not restore expected failures to accommodate a dependency update.

Native Tabs demonstrations with labels only still need actual content slots when a host wants meaningful tab-panel content. This is independent of hydration.

## Support checks

Release publication also requires the compatibility job for package types and local source operations on Linux and Windows. CI reads the supported Node range from `package.json`; the explicit minimum-version case in `.github/workflows/verify.yml` must be reviewed when changing that range. These jobs test the baseline, not every dependency combination.

Dependency updates arrive as reviewable Dependabot PRs; they are not merged automatically. Keep the Tiptap overrides coordinated. Remove the Guide hydration workaround only when the fixture passes without it on the supported dependency baseline, as described in [the hydration fixture](https://github.com/happydesigns/id/blob/main/tests/fixtures/guide/README.md).
