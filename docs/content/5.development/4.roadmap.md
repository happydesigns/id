The target workflow is: edit a brand, verify it in applications, generate a native Nuxt layer, then update each consuming application deliberately. Nuxt UI owns components and styling mechanisms; Nuxt owns layer composition. ID provides optional authoring and verification. Its editor should be replaceable by an upstream implementation without changing project storage or generated brands.

The [product vision](/concepts/product-vision) defines the intended DevTools and brand-portal experience, ownership and isolation boundaries. These are target capabilities, not an upstream commitment.

This page is the single status record for the agreed six steps. A release is a baseline, not completion of this roadmap.

| Step | Outcome | Status |
| --- | --- | --- |
| 1. Responsibilities | Identify required authoring, optional extensions and compatibility code. | Complete. See the architecture ownership table. |
| 2. Independent native output | Preserve user code and prove deterministic generation and standalone consumption. | Complete. Owned output is separate from user code; regeneration tests and two packed brand consumers verified, including standalone Studio and optional Guide builds. |
| 3. Replaceable editor | Separate theme controls from project lifecycle and demonstrate an alternative editor. | Complete. Controlled theme editor and alternative-editor browser proof. |
| 4. Independent app preview | Connect separately running apps through an explicit development integration. | Complete. Explicit development module and browser proof across two origins, with draft/original comparison and bounded app navigation. |
| 5. Full workflow proof | Two different apps with two brands, from draft through native builds. | Complete. Browser-edited exports build in a catalog and a dashboard with two brands; native appearance and app behavior match their light/dark previews. |
| 6. Reduction and upstream proposal | Remove proven redundancy and prepare a minimal contribution backed by the workflow. | Reduction pass implemented; current-state review precedes any upstream proposal. |

The v0.2.1 release is the baseline for this work. Keep one versioned package; split packages only when independent usage justifies it.


## Current-state review after the workflow proof

The native path has a demonstrated boundary: the authoring host owns documents, generated brands use native Nuxt configuration, and applications keep their own behavior. The editor is replaceable; built-in and app previews share draft application, and preview/export share CSS rendering. These are verified integration boundaries, not evidence of a complete upstream editor API.

The remaining maintenance cost is concentrated in three places:

- Studio's project coordinator still combines substantial UI and lifecycle orchestration. Unsaved-draft decisions are isolated and tested. Extract only independently useful responsibilities supported by tests; a smaller file alone is not a simpler architecture.
- Preview resets, icon presets and the component gallery retain Nuxt UI-derived definitions. Reset CSS prevents a host brand from leaking into another draft. The installed Nuxt UI package does not expose the complete reset/icon data as a ready-to-use public contract; replacing it with parsing of private build files would exchange visible duplication for fragile coupling.
- The published identity runtime, reference themes and legacy project export remain compatibility surfaces. They should not be expanded alongside native branding, but removing them requires an explicit breaking-change decision and migration.

Before proposing an upstream contribution, review these remaining responsibilities against concrete public Nuxt UI extension points and agree the compatibility horizon. Keep the proven app-preview and native-generation workflow as the acceptance test. No upstream proposal is part of this reduction pass.

## Upstream alignment

ID is a Nuxt-native complement, not a framework-neutral branding platform. Its own responsibility should shrink when public upstream capabilities cover the same use case.

| Area | Direction | Replacement condition |
| --- | --- | --- |
| Components, semantic styling, configuration and layer composition | Use Nuxt UI and Nuxt directly. | Reuse public contracts; do not duplicate their model. |
| Theme controls, copied gallery, icon presets and preview resets | Temporary integration code. | A supported upstream export covers the required behavior and passes the existing workflow checks. Do not import private documentation or build internals. |
| Editing brand projects, checking real apps and generating native layers | Current ID value and potential upstream contributions. | An upstream workflow preserves source ownership, app behavior and native consumption. |
| Metadata, assets and editorial guides | Optional brand-project needs. | Keep only demonstrated needs; Guide remains optional. |
| Generic adapters and identity runtime | Compatibility. | Removal requires an explicit breaking change and migration, not internal cleanup. |

Nuxt types are allowed in brand tooling. Generation remains side-effect-free and usable without an active application. Document validation, native generation, project scaffolding and archive output have separate internal modules while the public entrypoint remains compatible.

The next upstream discussion should demonstrate replaceable theme controls and previewing an application's own routes. Propose the smallest useful capability, backed by the two-app/two-brand workflow, rather than transferring the entire repository. There is no commitment to permanently retain ID-specific implementations of upstreamable features.

## Target-experience implementation plan

The earlier six steps establish the technical PoC. The following work proves the [product vision](/concepts/product-vision) without requiring a new multi-app framework. The starting worktree is clean and the vision is committed. Keep each implementation slice independently reviewable.

| Step | Deliverable | Acceptance | Status |
| --- | --- | --- | --- |
| A. DevTools host | A development-only editor view connected to the running application, reusing the existing controls and theme application. | Real DevTools entry; edit without reload; preserve inputs and navigation; undo and restore the exact original appearance; no production registration. | PoC verified through the real DevTools tab. |
| B. Published preview | Explicit preview-build integration for the same independently maintained playground. | Built preview connects to the portal with exact origins; normal production build has no preview bridge; no duplicated application. | PoC verified against a static production preview. |
| C. Capability proof | One company brand and two real capability playgrounds. | Exercise meaningful routes, validation, light/dark and responsive views; retain scenario ownership in each capability. | Verified with the maintained Course and Booking playgrounds and Rhein-Main brand. |
| D. Native adoption | Export the edited brand and build both capabilities against it. | Preserve app overrides and behavior; compare preview and native styles; no authoring runtime in consumers. | Verified in both real playground builds using a browser-exported brand. |
| E. Performance and upstream | Measured startup, edit latency, switching, transfer size and memory; reviewed proposal. | Optimize measured bottlenecks, document limits and prepare a small upstream integration proposal. | Initial local measurements recorded; controlled performance comparison and owner-reviewed upstream proposal remain. |

See [Real application proof](/development/capability-proof) for the repeatable C/D procedure, measured scope and remaining performance limits.

### Step A: implementation boundaries

- Use the supported DevTools extension API for the repository's installed stable version. Do not upgrade the framework to an experimental DevTools release for this PoC.
- Reuse StudioThemeEditor and document validation. Keep the DevTools host small rather than mounting a second complete Studio with its own app preview.
- Reuse native preview CSS/config application. Introduce explicit restoration of the captured host state; clearing a draft must not replace the original with generated default values.
- Keep the connection local to the current browser application through the DevTools client API. Do not broadcast edits to other visitors or introduce filesystem writes.
- Keep draft history and export deliberate. A DevTools view must never restyle itself instead of its target app. Initial connection must not change the target appearance.
- Register the editor route, tab and host plugin only in development. Keep the existing standalone Studio and external iframe workflow compatible.
- Test validation, original-state restoration, module registration and a browser journey through the real DevTools connection. Re-run existing preview tests for affected behavior, plus package build, lint and type checks. Document unverified limits rather than marking them complete.

### Subsequent experiments

Start performance measurements with the first working DevTools journey. For step B, reuse the same playground source and add an explicit preview build rather than enabling the existing development bridge in every production app. Verify asset and font resolution as well as brand/app override ownership. Keep independently built app isolation; a shared start command is sufficient orchestration for the PoC.

Before step C, inspect the selected capability projects and their existing playgrounds. Do not copy their pages into ID. Existing catalog/dashboard fixtures continue to protect the general contract but do not stand in for the real-capability proof.

After D and E, review and version the result for deliberate adoption by brand projects. Prepare the Nuxt UI editor/preview proposal separately from the Nuxt Core multi-app use case. Neither upstream publication nor releases are authorized by local implementation work.

## Remaining verification work

The earlier brand-system research is reflected in the native brand exports, source-derived brand references and the two-brand consumer checks. Remaining improvements, in priority order:

- Extend generator regression coverage across complete light/dark outputs and component defaults. Prefer focused assertions; use snapshots where reviewing the whole artifact adds value.
- Add pixel-based baselines only when their review and cross-platform maintenance are justified. The existing matrix compares representative computed styles, form errors and popovers across two widths and color modes; it does not assert screenshot equivalence.
- Extend compiled documentation examples as new public integrations appear. Published entrypoints and the preview example are already checked. Derive field-level contract documentation from schemas only if maintaining it starts to drift. Brand-value references already derive from the authoring source.
- Evaluate targeted checks for hardcoded brand colors in reusable examples, with explicit exceptions for palette displays and intentional demonstrations.

DTCG or Style Dictionary integration remains demand-driven, for a concrete design-tool interchange use case. It is not a runtime requirement or a prerequisite for the current product.
