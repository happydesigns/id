---
title: Releasing
description: Review, prepare and deliver a version through Changelogen.
---

The release command runs the complete [verification pipeline](/development/verification) through `pnpm verify:full` before Changelogen changes the version or creates a commit and tag. A failed check stops release preparation. Install Playwright's Chromium browser during setup as described in Verification. CI uses the same pipeline and additionally checks the supported operating-system and Node combinations.

## Versioned delivery

1. Use Conventional Commits. Run `pnpm release:preview` to inspect the generated entries without changing files, versions, tags or remote releases. Review public API compatibility and the proposed version.
2. For preparation without publication, run `pnpm release:prepare` from a clean worktree and let Changelogen infer the version from Conventional Commits. While the package is on v0, compatible changes including `feat` increment the patch version; breaking changes marked with `!` or a `BREAKING CHANGE:` footer increment the minor version. Review the actual API and dependency changes before release; commit labels do not prove compatibility. Use an explicit version override only for a reviewed exception. Changelogen generates the version, CHANGELOG.md, `chore(release): vVERSION` commit and annotated tag together. Do not hand-edit the version or manually tag a later test commit. Preparation does not push, publish to GitHub or publish to npm.
3. Review the generated commit and tag, then push the branch and its tag through the approved repository process (`git push --follow-tags` when authorized). Tag CI repeats all checks, verifies version and release-commit agreement, and automatically publishes a GitHub release containing the exact CI-built archive, checksum and that version's generated changelog. Prerelease tags produce prereleases. There is no separate GitHub-generated changelog and no manual draft-publishing step.
4. Registry publication and pushing require authorization; the combined `release` command performs both. GitHub CI needs no npm credentials; publication uses the local npm login. Changelogen synchronizes release text from the changelog. Asset uploads do not overwrite existing files; do not replace released assets or move tags.

ID has one versioned package; its private documentation and playground workspaces do not require Changesets. The ecosystem default is Changelogen; Changesets is an option when a repository releases multiple packages with independent or linked versions.

## Publishing to npm

For the complete authorized stable release, run:

```bash
nr release
```

The command checks npm authentication with `npm whoami`, runs `npm login` if needed, then runs `release:prepare`, `pnpm publish` and `git push --follow-tags` in order. Each step must succeed before the next starts. npm may request two-factor authentication during publication. The existing `prepack` lifecycle builds the package; public access is set in `publishConfig`. For prereleases, use the separate preparation flow with Changelogen prerelease options, then `pnpm publish --tag next` and push.

Use pnpm to publish from source: it replaces `catalog:` references with the ranges from `pnpm-workspace.yaml`. npm does not perform this conversion. CI also uses `pnpm pack` for its GitHub release archive. To publish those exact bytes instead, verify the release checksum and run `npm publish ./id-VERSION.tgz`.

If an npm version contains unresolved workspace or catalog references, publish a corrected patch version. Do not move its existing tag or replace its GitHub assets.

If publication fails after preparation, fix the failure and retry `pnpm publish`, then push. If publication may have succeeded despite a connection error, check `npm view @happydesigns/id@VERSION version` first. If only the push fails, retry `git push --follow-tags`. Do not rerun `release` to retry delivery of an already prepared version. Tag CI runs after npm publication; CI failure does not roll it back.

## Release text

`CHANGELOG.md` is the only source for GitHub release text. Keep Changelogen's categorized commit entries and contributor links. When useful, add a short summary and concrete upgrade notes above those entries, inside the same version section. Use level-three headings for these subsections; level-two headings are reserved for version boundaries. Small fixes do not need a separate summary.

Use the separate `pnpm release:prepare` flow for editorial review. Add editorial text after it has generated the entry, before pushing. Amend the unpushed release commit and recreate its local annotated tag to include the reviewed text; never move a tag that has already been pushed. CI uses `changelogen gh release` to synchronize that version from `CHANGELOG.md`. Do not use GitHub's Generate release notes button or maintain a separate summary file. Corrections to existing release descriptions should first be made in `CHANGELOG.md`, then copied to GitHub without changing the released tag or archive.

Until registry publication, consumers may install the reviewed release tarball as an exact file dependency with a committed lockfile. A checksum identifies the archive bytes; package.json identifies the API version. Do not silently replace an existing released archive.

Compatibility jobs and framework workaround requirements are documented in [Verification](/development/verification). The generated `CHANGELOG.md` owns version history and release notes; do not maintain a parallel release-notes directory.
