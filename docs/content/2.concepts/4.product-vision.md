## Purpose and status

Develop applications independently of a particular brand, then define and evolve their visual identity in one reusable native Nuxt layer. Support both a single application's theme and a company's shared brand across applications.

This is the agreed product direction, not a claim that Nuxt or Nuxt UI already provides these integrations. ID is the proof of concept and integration vehicle. Its implementation should shrink as supported upstream features replace it. Maintaining a separate editor or product is not an end in itself.

The [roadmap](/development/roadmap) owns implementation status and next steps. The [Studio guide](/guides/brand-studio) describes features available today.

## User journeys

| Need | Intended experience |
| --- | --- |
| Theme one application | Open the editor in Nuxt DevTools and use the running application itself as the preview. No separate Studio application is required. |
| Develop a company brand | Start from a preset or existing brand, define palettes, typography, assets and component defaults, and check relevant applications. |
| Evaluate capabilities | Try the company brand with real happydesigns capability playgrounds, such as Course and Booking, including meaningful content and interaction states. |
| Maintain a brand portal | Publish brand guidance and interactive previews in a browser-accessible host. Editing and export are optional; Docus is optional. |
| Share branding across apps | Export or update a versioned native Nuxt layer. Each application deliberately adopts the version and rebuilds or redeploys. |
| Review a change | Compare original and draft, check light/dark and responsive layouts, and retain application interaction state where possible. |

A theme cannot automatically restyle hardcoded application colors or arbitrary third-party widgets. A shared brand does not guarantee design quality. Applications must use the supported semantic styling and asset contracts.

## One foundation, two interfaces

Theme controls and preview integration must be reusable outside either host. DevTools must not become a requirement for a published brand portal, and the portal must not become a requirement for local editing.

~~~text
Reusable theme editor + draft lifecycle + preview connection
                         |
              +----------+----------+
              |                     |
       Nuxt DevTools           Brand portal
       Local application       Browser-accessible previews
                               Optional editorial guide
                         |
              Deliberate apply / export
                         |
            Native config + CSS + assets
                         |
          One app or a shared Nuxt brand layer
~~~

The editor proposes changes; the host owns draft history, persistence, review and application to source. Previewing is temporary. Saving a local draft is not publishing a company brand. Production consumers need Nuxt UI and their brand configuration, not the authoring editor or preview bridge.

A playground is still a running Nuxt application. DevTools removes the need for a separate authoring application, not the need for a host in which to develop a standalone theme.

## Reuse the real playground

Maintain application and scenario code once. A capability's existing playground should serve development, testing and embedded brand previews. Do not maintain a second imitation of the capability inside ID or the portal.

For a published portal, the same playground source may need its own build and deployment. Reusing code does not imply sharing a build or runtime.

Two preview modes are useful:

- Controlled component scenarios can be loaded directly into a host when sharing its configuration is intentional.
- Complete playgrounds and applications need their own configuration and runtime boundaries. A preview bridge applies drafts, reports readiness, supports agreed navigation and restores the original theme. It should avoid reloading the app for ordinary token changes.

Published previews use suitable example data. Cross-origin connections require explicit origin and message validation; neither embedding nor a shared domain is a security boundary by itself.

## Isolation and orchestration

Nuxt layers compose one application; they do not fully isolate imports, plugins, routes, app configuration, global CSS or dependencies. Namespacing and local style overrides help controlled scenarios but cannot turn an arbitrary application into an isolated layer.

An iframe can separate browser documents and viewports. A preview route in the same Nuxt build still shares its build configuration. Independently configured applications may need separate builds and execution contexts even when tooling presents a single start command and a common portal URL.

The desired experience is to register an existing playground and let tooling manage its start, address and connection. Package layout, process management and iframe usage remain implementation choices. Do not make a new general-purpose isolation framework a prerequisite for theme editing.

Nuxt's [multi-app tracker](https://github.com/nuxt/nuxt/issues/21635) is a relevant upstream discussion, not a promised solution. [Layer isolation discussions](https://github.com/nuxt/nuxt/discussions/29676) provide related use cases. Prefer contributing the concrete preview requirement to that work over prescribing an isolated-layer API in advance.

## Intended ownership

| Responsibility | Target owner |
| --- | --- |
| Components, semantic styling and native configuration | Nuxt UI and Nuxt, using public APIs. |
| Reusable theme controls and DevTools entry | Proposed Nuxt UI integration; current ID controls remain replaceable. |
| Theme application to previews | A small reusable connection usable from DevTools and portals; proposed upstream responsibility. |
| Multi-app execution and orchestration | Potential Nuxt Core integration, independently useful beyond branding. |
| Capability behavior, example content and scenarios | Each capability or application. |
| Company assets, visual decisions and editorial guidance | The brand project. |
| Workflow proof and temporary integration gaps | ID, until supported replacements cover the demonstrated needs. |

Do not import private Nuxt UI website internals as stable APIs. Its current template views are directly rendered examples in the documentation app, not proof of a public external-app preview interface. See the upstream [home page](https://github.com/nuxt/ui/blob/v4/docs/app/pages/index.vue) and [SaaS view](https://github.com/nuxt/ui/blob/v4/docs/app/components/theme-studio/view/ThemeStudioViewSaas.vue).

## Performance expectations

Measure production builds before claiming parity with ui.nuxt.com. Track initial usable content, edit-to-visible-update latency, preview-switch latency, transferred JavaScript/fonts and memory under comparable conditions.

Load selected previews on demand; initialize comparison only when requested. Keep unrelated editor/export work out of the initial viewing path. Preserve the running preview during ordinary theme changes. Use measurements to select optimizations instead of introducing blanket caches or speculative infrastructure.

## Upstream proposal boundary

Prepare one coherent user-facing vision with independently useful implementation steps:

1. Nuxt UI: reusable editor, DevTools integration, temporary live application theming and native output.
2. Preview extensions: existing playgrounds and application routes, reusable from a browser brand portal.
3. Nuxt Core: the preview use case for multi-app isolation and orchestration, linked to existing work.

Exact APIs, packaging and adoption belong in discussion with maintainers. Keep logos, portal guidance and company workflows extensible rather than requiring the entire ID document model upstream.

Any issue, discussion, comment or pull request upstream requires the owner's explicit review and approval before publication. Preparing evidence and a local proposal does not authorize posting it.
