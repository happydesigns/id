## Theme exports

```ts [theme-imports.ts]
import { nuxtUiBrandTheme } from '@happydesigns/id/themes/nuxt-ui'
import { sampleBrandTheme } from '@happydesigns/id/themes/sample-brand'
```

The root package re-exports the Nuxt UI baseline for convenience. The theme subpaths make it clear whether a project is using the standard baseline or the neutral sample brand demonstration theme. That local theme exists to show the `id` contract; `@happydesigns/brand` owns the final happydesigns guide and assets.

## Layer export

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: ['@happydesigns/id/nuxt']
})
```

The package export points to the public identity layer. It registers Nuxt UI, the `Id` runtime components, and identity CSS. It does not include repository-only tooling such as `@nuxt/eslint`.

Layer components are prefixed with `Id`. `IdNuxtUiDocsLink` renders compact links to Nuxt UI documentation and accepts either typed links or an MDC-friendly string:

```mdc [component-docs.md]
::id-nuxt-ui-docs-link{links="UButton|https://ui.nuxt.com/docs/components/button; UTooltip|https://ui.nuxt.com/docs/components/tooltip"}
::
```

`IdExampleFrame` provides a neutral surface for visible brand-guide examples:

```mdc [component-docs.md]
::id-example-frame
  <!-- Brand-owned example content stays here. -->
::
```

Use `variant="plain"` when the example already owns its own frame or layout surface.

`IdLayerInstall` renders a brand-neutral install surface for package-backed brand layers:

```mdc [landing.md]
::id-layer-install{package-name="@client/brand" title="Build with the layer."}
::
```

Use the `layer` prop when the installed package and Nuxt layer export differ.

The default renderer composes Nuxt UI's standard `ProseCodeGroup` and `ProsePre` components directly, with Shiki rendering the highlighted slot content. In a custom context, pass a slot and render `snippets.installCommand` and `snippets.nuxtConfig` with the host app's own code component.

Use guide-section helpers when a brand source file owns richer section metadata for cards, navigation, or page headers:

```ts [brand-guide.ts]
import { createGuideDocsSections, defineBrandGuide, defineGuideSections } from '@happydesigns/id'

export const sections = defineGuideSections([
  {
    slug: 'colors',
    title: 'Colors',
    description: 'Palette, semantic roles, and usage guidance.',
    icon: 'i-lucide-palette'
  }
])

export const guide = defineBrandGuide({
  name: 'client',
  title: 'Client',
  description: 'Client brand guide.',
  docs: {
    sections: createGuideDocsSections(sections)
  }
})
```

`IdComponentCoverageTable` renders the current guide's component coverage from `id.guide.componentCoverage`:

```mdc [coverage.md]
::id-component-coverage-table
::
```

Pass explicit `items` from Vue when the table should render a subset instead of the app-config guide, or when an extending brand layer needs to avoid Nuxt app-config array merging from lower layers.

## Module export

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@happydesigns/id/module'],
  id: {
    name: 'client',
    componentPrefix: 'Id'
  }
})
```

The layer export uses the `Id` component prefix. The module can use another global prefix when a host app needs to avoid naming collisions. Docus and Nuxt Content keep ownership of markdown parsing and prose highlighting.

## App config

```ts [app.config.ts]
export default defineAppConfig({
  id: {
    name: 'client',
    theme: clientTheme,
    guide: brandGuide
  }
})
```

Use `id.name` and `id.theme` for normal brand layers. Use `id.themes[]` and `id.defaultTheme` only for apps that intentionally ship multiple runtime-selectable themes. `IdThemeSelect` scopes persisted runtime-theme choices through `createBrandThemeCookieName(id.name)` and its Nuxt state through `createBrandThemeStateKey(id.name)`.

## Brand assets

`id.guide.assets.logos` is a typed `Record<string, BrandAsset>`. Known role names such as `logo`, `wordmark`, `symbol`, `mark`, and `appIcon` are conveniences only. Brand layers may define any role name that matches their identity system.

Prefer keeping durable guide asset entries in the brand source file, then mapping them into runtime assets:

`IdLogo` reads that map and can render a specific role:

```vue [BrandLogo.vue]
<IdLogo role="crest" />
```

Without a role, it renders the first common logo role it can find, then falls back to the first configured asset, then to the brand title. `media` defaults to `auto`, so `IdLogo` follows the active color mode. Dark-media selection prefers common inverse roles such as `wordmarkInverse` and `symbolInverse` before the light-surface roles. Pass `media="light"`, `media="dark"`, or `media="any"` to force a specific treatment.

For custom components, use the same asset selection logic through `useBrandAssets()` or the framework-neutral helpers:

```ts [brand-assets.ts]
import { collectBrandAssets, createBrandGuideAssets, selectBrandAsset } from '@happydesigns/id'

const guideAssets = createBrandGuideAssets([
  {
    name: 'Client signature',
    role: 'signature',
    path: '/brand/signature-dark.svg',
    usage: 'Footer signature for dark surfaces.',
    media: 'dark',
    alt: 'Client signature'
  }
])

const asset = selectBrandAsset(collectBrandAssets({ assets: guideAssets }), {
  role: 'signature',
  media: 'dark'
})
```

## Validation error

Invalid contracts throw `BrandValidationError` with an `issues` array. Use that list in CLI or editor workflows to show actionable errors.
