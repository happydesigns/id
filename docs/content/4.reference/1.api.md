## Local DevTools editor

`@happydesigns/id/devtools` is an optional development-only Nuxt module. It registers the **Brand theme** DevTools tab, an editor route and a client host connection. It adds none of these when building production or when DevTools is explicitly disabled. Optional `document` supplies the editable brand source; optional `appUi` identifies application overrides that remain authoritative. See [DevTools editing](/guides/brand-studio#edit-the-running-app-in-devtools).

## Independent app preview

`@happydesigns/id/preview` exports an optional Nuxt module and the `PreviewOptions` type. Required options are `studioOrigin` (an exact HTTP(S) origin) and `id` (the Studio template ID). `routePrefix` defaults to `/`; optional `brandUi` identifies the native brand defaults to replace. Optional `appUi` contains explicit app overrides applied after the draft, including values equal to the previous brand. The module registers only a client preview plugin, only in development. See [the Studio guide](/guides/brand-studio#preview-a-separately-running-app) for both sides of the connection.

### Typed preview configuration

This standalone example uses explicit app defaults. In a real app, import the same `appUi` object into both this configuration and `app/app.config.ts`; add the original brand's UI config as `brandUi` when replacing an installed brand.

```ts [preview.config.ts]
import { defineNuxtConfig } from 'nuxt/config'
import preview from '@happydesigns/id/preview'
import type { PreviewOptions } from '@happydesigns/id/preview'

const options: PreviewOptions = {
  studioOrigin: 'http://localhost:3000',
  id: 'shop',
  routePrefix: '/shop',
  appUi: { button: { defaultVariants: { variant: 'outline' } } }
}

export default defineNuxtConfig({ modules: [[preview, options]] })
```

## Theme exports

```ts [theme-imports.ts]
import { nuxtUiBrandTheme } from '@happydesigns/id/themes/nuxt-ui'
import { sampleBrandTheme } from '@happydesigns/id/themes/sample-brand'
```

The root package re-exports the Nuxt UI baseline for convenience. The theme subpaths make it clear whether a project is using the standard baseline or the neutral sample brand demonstration theme. That local theme exists to show the `id` contract; `@happydesigns/brand` owns the final happydesigns guide and assets.

## Adapter exports

Import maintained adapters from explicit subpaths:

```ts [brand.ts]
import { nuxtUiAdapter } from '@happydesigns/id/adapters/nuxt-ui'
import { cssVariablesAdapter } from '@happydesigns/id/adapters/css-variables'
```

Users define other adapters with `defineBrandAdapter()`. Adapters are normal TypeScript modules; `id` has no registry or discovery mechanism.

`NuxtUiColorRole` intentionally combines the current well-known literal suggestions with an open string type. Known roles remain discoverable in editors, while future Nuxt UI or project-specific roles can be mapped without changing `id` first.

## Layer export

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  extends: ['@happydesigns/id/nuxt']
})
```

The package export points to the public identity layer. It registers Nuxt UI, the runtime components `IdLogo`, `IdThemeSelect`, and `IdColorModeButton`, plus identity CSS. It does not include repository-only tooling or brand-guide components.

## Guide layer export

Guide applications add documentation helpers explicitly:

```ts [docs/nuxt.config.ts]
export default defineNuxtConfig({
  extends: ['@example/brand', '@happydesigns/id/guide', 'docus']
})
```

The guide export is an add-on, not a standalone brand runtime. Its components use the same `Id` prefix. `IdNuxtUiDocsLink` renders compact links to Nuxt UI documentation and accepts either typed links or an MDC-friendly string:

```mdc [component-docs.md]
::id-nuxt-ui-docs-link{links="UButton|https://ui.nuxt.com/docs/components/button; UTooltip|https://ui.nuxt.com/docs/components/tooltip"}
::
```

`IdExampleFrame` provides a neutral surface for visible brand-guide examples:

```mdc [component-docs.md]
::id-example-frame
  <!-- Brand-owned example content stays here. -->
::
```

Use `variant="plain"` when the example already owns its own frame or layout surface.

`IdComponentExample` renders the reusable Nuxt UI component examples shipped by `id`:

```mdc [component-docs.md]
::id-component-example{name="button" frame="none"}
::
```

Use the `context` prop from Vue when a brand layer wants the defaults to use brand-owned package names, docs paths, logo assets, accent color, or sample copy. Brands can override a single example with a named slot instead of forking the whole renderer.

The source helpers are exported for brand-owned guide code:

- `componentExampleFamilies`
- `componentExampleGroups`
- `componentExampleNames`
- `componentExampleOwnSurfaceNames`
- `createComponentExampleContext`
- `defineComponentExampleContext`
- `getComponentExampleDefinition`
- `isComponentExampleName`

`IdLayerInstall` renders a brand-neutral install surface for package-backed brand layers:

```mdc [landing.md]
::id-layer-install{package-name="@client/brand" title="Build with the layer."}
::
```

Use the `layer` prop when the installed package and Nuxt layer export differ.

The default renderer composes Nuxt UI's standard `ProseCodeGroup` and `ProsePre` components directly. That gives the install surface the standard tabs, filenames, copy button, and code surface, but it does not run a syntax highlighter by itself. Syntax highlighting belongs to the host documentation pipeline. Pass a slot when a Docus or Nuxt Content app needs to render `snippets.installCommand` and `snippets.nuxtConfig` through its own highlighter-backed code component.

Use guide-section helpers when a brand source file owns richer section metadata for cards, navigation, or page headers:

```ts [brand-guide.ts]
import { createGuideDocsSections, defineBrandGuide, defineGuideSections } from '@happydesigns/id'

export const sections = defineGuideSections([
  {
    slug: 'colors',
    title: 'Colors',
    description: 'Palette, semantic roles, and usage guidance.',
    icon: 'i-lucide-palette'
  }
])

export const guide = defineBrandGuide({
  name: 'client',
  title: 'Client',
  description: 'Client brand guide.',
  docs: {
    sections: createGuideDocsSections(sections)
  }
})
```

`IdComponentCoverageTable` renders the current guide's component coverage from `id.guide.componentCoverage`:

```mdc [coverage.md]
::id-component-coverage-table
::
```

Pass explicit `items` from Vue when the table should render a subset instead of the app-config guide, or when an extending brand layer needs to avoid Nuxt app-config array merging from lower layers.

## Module export

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['@happydesigns/id/module'],
  id: {
    name: 'client',
    componentPrefix: 'Id'
  }
})
```

The module declares `@nuxt/ui` as a Nuxt module dependency, then registers the `Id` components, composables, CSS, theme plugin, and app-config types. Use the layer export instead when a brand package should be consumed through Nuxt's `extends` chain.

The layer export uses the `Id` component prefix. The module can use another global prefix when a host app needs to avoid naming collisions. Docus and Nuxt Content keep ownership of markdown parsing and prose highlighting.

## App config

```ts [app.config.ts]
export default defineAppConfig({
  id: {
    name: 'client',
    theme: clientTheme,
    assets: brandAssets
  }
})
```

Use `id.name`, `id.theme`, and optional `id.assets` for normal brand layers. This is typed as `BrandRuntimeOnlyConfig`. A guide application may additionally expose `id.guide` through `BrandGuideAppConfig`; ordinary consuming apps do not need it. `BrandRuntimeConfig` remains the backward-compatible combined type name. Use `id.themes[]` and `id.defaultTheme` only for apps that intentionally ship multiple runtime-selectable themes. `IdThemeSelect` scopes persisted runtime-theme choices through `createBrandThemeCookieName(id.name)` and its Nuxt state through `createBrandThemeStateKey(id.name)`.

In Vue components, `useBrandGuide()` reads the public guide from `app.config.id.guide` and falls back to the shipped `id` baseline guide when no brand layer has configured one. Keep richer page-source content in the concrete brand package when a homepage or docs page needs brand-specific arrays beyond the public `BrandGuide` contract.

## Runtime composables

The Nuxt layer and module auto-import these composables for Vue components in host apps:

| Composable | Purpose |
| --- | --- |
| `useBrandGuide()` | Read the public `id.guide` contract from app config, with the neutral `id` guide as fallback. |
| `useBrandAssets()` | Resolve `id.assets`, falling back to legacy `id.guide.assets`, and select logo roles. |
| `useBrandTheme()` | Read, apply, and persist the active runtime theme from `id.theme` and optional `id.themes[]`. |

These composables only read public app-config identity data and shipped theme values. They do not load remote brand behavior, private data, or uncompiled components.

## Brand assets

`BrandAssets` is independent from `BrandGuide`. A neutral `BrandDefinition` may carry it as `assets`, and an app can expose the same value as `id.assets`. `id.guide.assets` remains a compatibility fallback for guide apps. Known role names such as `logo`, `wordmark`, `symbol`, `mark`, and `appIcon` are conveniences only. Brand layers may define any role name that matches their identity system.

Author runtime assets directly on the neutral definition when no richer guide metadata is needed. `createBrandGuideAssets()` remains useful when documented guide entries with `usage` text are the original source.

`IdLogo` reads that map and can render a specific role:

```vue [BrandLogo.vue]
<IdLogo role="crest" />
```

Without a role, it renders the first common logo role it can find, then falls back to the first configured asset, then to the brand title. `media` defaults to `auto`, so `IdLogo` follows the active color mode. Dark-media selection prefers common inverse roles such as `wordmarkInverse` and `symbolInverse` before the light-surface roles. Pass `media="light"`, `media="dark"`, or `media="any"` to force a specific treatment.

For custom components, use the same asset selection logic through `useBrandAssets()` or the framework-neutral helpers:

```ts [brand-assets.ts]
import { collectBrandAssets, createBrandGuideAssets, selectBrandAsset } from '@happydesigns/id'

const guideAssets = createBrandGuideAssets([
  {
    name: 'Client signature',
    role: 'signature',
    path: '/brand/signature-dark.svg',
    usage: 'Footer signature for dark surfaces.',
    media: 'dark',
    alt: 'Client signature'
  }
])

const asset = selectBrandAsset(collectBrandAssets(guideAssets), {
  role: 'signature',
  media: 'dark'
})
```

## Validation error

Invalid contracts throw `BrandValidationError` with an `issues` array. Use that list in CLI or editor workflows to show actionable errors.

## Guide messages and authoring host

`componentExampleMessages` exposes the English fallback catalog. `resolveComponentExampleMessage` (`messages, key`) resolves optional `ComponentExampleMessages` overrides per key. Pass `messages` through `IdComponentExample` context. Actions, forms, navigation, data and overlays are covered; other families retain their existing copy contracts. Nuxt UI built-in labels use its own locale configuration. Model values, technical component names and routes are never translated.

`ComponentCoverageLabels` overrides headers and per-status label/description; `resolveComponentCoverageStatus` (`status, labels`) retains colors and missing English values. `caption` and `emptyText` stay separate props.

`StudioHostConfig` types the existing `idStudio` host configuration (also exported from studio/core). It contains document, brands, sourcePath, home, documentation, host, templates and optional packageAsset. It is trusted app configuration, not imported brand data.

Use `IdStudioLink` with an optional translated label inside Docus AppHeaderCTA and AppFooterLeft. It renders a native neutral button only when the Studio route is installed. Docus keeps its header, footer and mobile navigation; customers keep their landingpage. Backlinks use idStudio.home and documentation.
